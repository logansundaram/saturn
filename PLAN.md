## The spine

**Watch it, gate it, replay it — on hardware you own.** Features that strengthen those three verbs are the product. Everything else is substrate: keep it working, spend nothing on it. Decision knives already in the repo: "if a competitor shipped this tomorrow, would anyone switch to you for it?" · new surfaces must be legible views over existing instrumentation, never new capability · no claim before its mechanism.

Brand frame that unifies the moat: **the human can take the pen at any altitude** — the plan (author / veto / steer), the step (the gate), the token (freeze-edit-continue). All enforced, all in the trace.

## Moat — hone these (ranked)

1. **Token steering + confidence coloring** (freeze → edit → continue, provenance-tagged; low-confidence runs render red). Unique in the competitive set; the demo GIF and launch hook; structurally hard for cloud agents to copy.
2. **The living plan as control surface** — review, veto, mid-run steer (Magentic-UI's 30→52% co-planning result is the thesis evidence).
3. **The approval gate showing the real artifact** — exact command, colored diff, quarantine escalation, one policy object, fail-closed defaults.
4. **The replayable run record** — `/trace export` → offline `--replay`, `/trace why`. The audit seed: what acquirers historically paid for and the EU Art. 26(6) story.
5. **Egress receipt + air-gap + keyless web** — "nothing leaves" as an observable fact.
6. **The trust benchmark** — currently a smoke suite; strategically the category artifact ("own the measuring stick"). All spare engineering goes here before any new capability.

Near-term investment, in that spirit: steering demo GIF · deterministic write sentinel (converts a model-judged heuristic into an enforced claim) · benchmark v1 to the G1 bar · first-run reliability.

## Evaluated addition (2026-07-15): user-authored plans ("runbook mode") — moat-consistent, thin slice only

Owner's insight: invert plan authorship — the user drafts the plan, the agent executes it. Assessment: **yes, on-moat** — the far end of the authorship dial and the completion of "the plan is the control surface." Three legs make it moat rather than gimmick:

1. **Reliability** — at 2–4B local models the planner is the flakiest node (bench history: plan parse failures, the L3 26-step balloon). A user-authored plan deletes the weakest LLM call for exactly the repeated/high-stakes tasks that matter; execute/rectify (the strong parts) do the rest.
2. **Security** — the CaMeL ideal realized: control flow authored by the trusted principal before untrusted-data contact. Untrusted content can fill parameters; it can never have authored a step.
3. **Audit/enterprise** — human-authored procedure + agent execution + replayable record = a runbook with proof of execution. "Runbooks → agents" is an active 2026 ops wave (Cutover, myrunbook.com, RunbookAI — all cloud SaaS); nobody does it local + gate-enforced + replayable. "The runbook was followed — here's the replay" is the regulated-buyer sentence.

Honest caveat: the inversion alone is copyable (any agent can "execute my TODO.md"; workflow tools have owned human-authored automation forever). The defensible thing is the feature inside Saturn's envelope — same logic as the benchmark.

**Scope guard (the recipes/user-commands graveyard warns here):** one thin slice, not a workflow platform. User supplies a step list (pasted checklist, `@runbook.md`, or `/plan draft`); it parses into the SAME step dicts the engine runs, with `author: user` provenance per step; agent binds tools/args at runtime through unchanged gates; **rectify/replan may not silently rewrite a user-authored step** — dead ends pause and propose (precedent: plan_vetoes — human edits outrank engine self-correction); provenance renders in trace/replay (that IS the audit artifact). Explicitly NOT: recipe libraries, parameterized templates, scheduling, a DSL — re-paste the plan each run until design partners pull otherwise. Build cost is small (plan is already the data bus; deferred binding already handles fuzzy targets). Priority: after benchmark v1; candidate second demo + Phase 2 deep-dive post.

**Status [verified 2026-09-01]:** the reliability leg is shipped and the other two are not.
- Shipped: `/draft` (`commands/plan.py`) opens the same step editor as mid-turn review on an empty plan; the REPL seeds the draft into the next turn and `nodes/plan.py` honors a pre-seeded plan verbatim, skipping the planner LLM call. Tool spellings normalize through the same synonym table as the planner; unresolvable names fail closed at execution.
- Not built: (1) no `author` field on step dicts — the step vocabulary is `step_id/label/status/intended_tool/result/needs_resolution`, the only provenance key is `origin: replan`, and `plan_ops.normalize`'s whitelist would drop an `author` key if one were added upstream; (2) rectify/replan can still silently rewrite a user-drafted step — the only human-outranks-engine rule keys on *vetoes* (steps the user removed), not on authorship, and nothing pauses-and-proposes at a dead end; (3) provenance never reaches the trace, export, or replay — trace deltas record `status:label` only, the plan panel renders no authorship marker, and the sole user-facing signal is a transient REPL note; (4) no pasted-checklist or `@runbook.md` seeding — `@file` expands to an attachment block only; (5) a draft is consumed by one turn. Docs: CHANGELOG describes `/draft` as co-planning, FEATURE_INVENTORY has no row for it, "runbook" appears nowhere but here.
- Reading: the moat legs (security, audit) are exactly the unbuilt ones. Build order is (1) → (2) → (3) before any demo; (4) after; (5) stays out of scope per the scope guard.

## Evaluated framing (2026-09-01): "Claude Code for daily tasks" — two readings, two very different scores

Owner's stated ambition: Saturn should be the Claude Code equivalent for daily tasks, not coding. Assessed against the repo (main, Aug 2026), the Tool Suite doc, and the Aug 17 review. The phrase has two readings and Saturn scores differently on each.

**Reading 1 — the interaction model: largely built, in places ahead.** Claude Code's shape is terminal-native, plan → execute loop, permission prompts before side effects, sessions/resume, @file mentions, slash commands, MCP extensibility, headless mode. Saturn has every one, and exceeds it where the moat lives: the plan as an editable control surface, token-level freeze-edit-continue, the replayable trace. Structurally Saturn IS the Claude Code shape pointed at general tasks.

**Reading 2 — the competence level: not close, partly by design.** Three gaps, in severity order:

1. **The model ceiling.** Claude Code's magic is mostly the frontier model behind it. Saturn runs 2–27B local models, and the bench history says the planner is the flakiest node (plan parse failures, the L3 26-step balloon). No scaffolding makes this class of model handle open-ended multi-step tasks the way people experience Claude Code. The architecture — gates, rectify, and above all runbook mode, which deletes the weakest LLM call for exactly the repeated daily tasks that matter — is the correct compensation, but the ceiling on "just ask it anything" competence is structural. _(Materially revised by the 2026-09-01 addendum below.)_
2. **The tool surface doesn't cover daily life.** Shipped and frozen: files, shell, calculator, GET-only web fetch, local RAG, ask_user, memory. That handles the local half of daily tasks well (organize files, summarize a PDF, batch-rename, look something up). The other half — email, calendar, messaging, the browser — is explicitly refused native (Tool Suite doc) and deferred to MCP at v2.0. Today a user asking Saturn to "reply to that email and move my 3pm" hits a wall Claude Code users never hit in their domain.
3. **Reliability of what exists.** The Aug 17 review found three ship-blockers where the trust mechanisms themselves break (the gate's `a` keypress disabling the revocation lock, the calibrated exit threshold never read, REVOKE_ALL over-revocation); first-run on macOS/Linux unverified; benchmark still a smoke suite. When the compensating story is "you can trust and steer it," the trust machinery must be airtight before the capability gap is forgivable. **[verified 2026-09-01: all three are fixed on main with tests** — the revocation lock now reads the frozen `DECLARED_RISK` snapshot instead of the grant-mutable live tier (53a31f1, re-hardened bf6d66d; `tests/test_revocation.py`); enter/exit thresholds resolve as a pair so the table's measured exit is actually consulted (b843da9; `tests/test_confidence.py`); REVOKE_ALL is minted only for write/shell effects and applied blanket only to filesystem tools, with collateral kills disclosed (bf6d66d; `tests/test_revocation.py`). A second-`a` grant-permanence regression found in the same pass was also fixed. **This gap is closed; the trust story is true again, and the remaining work is capability, not trust.]**

**The tension with this doc's own spine.** The spine classifies "useful-enough" (the daily-task substrate) as frozen — zero new investment — precisely because Saturn cannot win a raw-capability fight against cloud frontier agents from local small models. "Claude Code equivalent for daily tasks" as a literal goal is a pivot away from that. If it becomes the goal, the path is not a smarter planner; it is (a) runbook mode shipped as the way repeated daily tasks become reliable (user authors the plan once, Saturn executes it gated every run), and (b) MCP integrations pulled forward from v2.0, because calendar/email IS daily tasks — behind the gate, untrusted, per the Tool Suite doc's existing rules, never native. Both are already on the roadmap; the open decision is whether they move from "later/thin slice" to the center. Until that decision is made deliberately, the spine stands.

**Honest scorecard (Sep 2026):** as a control surface and agent skeleton, at par with or ahead of Claude Code. As a thing a normal person hands their daily tasks to, roughly 30–40% of the way — strong on local files and lookups, absent on integrations, capped by small-model planning — with the trust story (the real differentiator) requiring the three gate bugs fixed to be true. **[verified 2026-09-01: the gate bugs are fixed, so the trust story holds. The "strong on local files" half is weaker than this line says — see the Verification pass: the file tools are jailed to a fixed configured folder rather than the launch directory, and `read_file` cannot open a PDF or .docx. Revised: ~35% on 27b-capable hardware, lower on the default 4b install; the cheapest large gains are workspace-at-cwd and direct document reads, neither of which the sections above name.]**

- **RAG — the big affordable cut: demote, don't delete.** Off-moat (nobody switches for RAG), and the most expensive substrate: the embedder pull exists only for it, it costs startup sync time, and it breeds its own roadmap (tuning UI, OCR, scoping, workspace/documents confusion — all already deferred). Action: lazy embedder pull on first `/docs add` (drops multi-GB from the default install), freeze all RAG investment, keep `search_knowledge_base` + citations working for the air-gapped-corpus enterprise story.
- **`/privacy redact`** — dormant since the cloud shelve (guards only a remote `OLLAMA_HOST`). Shelve with cloud support or leave frozen.
- **Capability benchmark suites** — CI regression only; benchmark energy goes to the trust benchmark.
- **Hold existing cuts/shelves:** recipes, user-defined commands, background jobs, `/dryrun`, token budget, cloud models, phase-3 crypto (no signing before design partners), TUI prompt machinery, the art. Formal scope cuts stay cut: GUI, consumer integrations, coding-agent specialization, vision.

## Verification pass (2026-09-01) — gaps the sections above did not name

Read against main @ b843da9 with the "Claude Code for daily tasks" question in mind. Ordered by how much each blocks daily use; the first two are substrate fixes, not new capability, and are the cheapest large gains in the repo.

1. **The file tools do not operate where you launched.** `tools/files.py::_resolve` roots every path at `get_config().path("workspace")` — a fixed folder, `database/workspace`. Claude Code's single most important daily-task property is that it works in the directory you ran it from; "organize my Downloads," "rename these photos," "summarize the PDF on my desktop" all refuse before the model is consulted. Fix: a launch-directory workspace mode (flag or config), same sandbox check rooted at cwd; keep the fixed workspace as the installed-mode default if wanted. `/undo` snapshots and SATURDAY.md discovery follow the same root.
2. **`read_file` cannot open the files people actually have.** UTF-8 text only; PDF and .docx are readable only via `/docs add` + `search_knowledge_base` — i.e. through the subsystem this doc demotes. Fix: route `read_file` through the loaders already in `stores/rag.py` (pypdf, python-docx) for a direct read. This is what makes the RAG demotion safe: "summarize this PDF" stops depending on the embedder.
3. **MCP: the mechanism is right, the distance to a first integration is undocumented.** Same gate, risk fails closed to `destructive`, always `untrusted` → quarantine-scanned, `${VAR}` from `.env`. But `servers: {}` ships empty, the github/internal-docs examples are commented out, and every remote call prompts until the user hand-edits YAML and sets a tier. The concrete form of the "pull MCP forward" decision is one working example enabled by one command (a read-only calendar or filesystem server with a documented tier) — it does not require breaking "never native."
4. **No scheduling, by decision.** Cut with background jobs; consistent with the gate. It means "daily" cannot mean recurring inside Saturn. The honest shape is runbook mode + headless `-q` + the user's own cron; nothing documents that path. Document it rather than build it.
5. **Per-step latency is unmeasured.** Every step is ≥2 LLM calls (execute, then rectify's judge) plus an occasional replan. On 27b this is tolerable; on the default 4b tier it is where the "flaky planner" experience actually comes from. Benchmark v1 should report wall-clock per step alongside the trust rates.
6. **Doc rot.** CLAUDE.md missing (21 pointers). Tool Suite doc not in repo. `docs/FEATURE_INVENTORY.md` still lists Tavily and `http_request` and has no `/draft` row (it is a pre-2026-07-03 snapshot by its own header — either mark every row stale or retire it). `docs/ARCHITECTURE.md` points at an untracked `documentation.md` that does not exist.

## The pitch each pillar serves

Private/local (egress + air-gap + keyless) · Visible (plan + trace) · Controlled (gate + steer + author) · Auditable (export + replay) · Useful-enough (files/shell/web/docs — the frozen substrate). Anything that serves only "useful-enough" gets no new investment.
